# MoonBit 移植プロジェクト選定ガイド

fd_mbt, beads_mbt 等の実経験に基づく、**「どのプロジェクトを移植すべきか」**の判断基準。

---

## 移植適性マトリクス

| 適性 | 特徴 | 具体例 |
|---|---|---|
| **◎ 本命** | 純粋なデータ変換、入出力明確、依存少ない、テスト充実 | `gron`, `jq` (簡易版) |
| **○ 対抗** | ファイル走査系、既存資産流用可能、テスト充実 | `tokei`, `du-dust` |
| **△ 保留** | ネットワークI/O、並列処理、AST操作、TUI | `ripgrep`, `bat`, `xh`, `bandwhich` |
| **✕ 回避** | OS固有機能多用、カーネルレベル、GUI | `hyperfine` (一部), `bottom` |

---

## MoonBit でテストを戦える条件

### ✅ テストが機能するプロジェクトの特徴

1. **テストスイートが充実している**
   - `cargo test` / `go test` で緑が並ぶ
   - `tests/` ディレクトリにフィクスチャが豊富
   - Codecov/Coveralls バッジがある

2. **入出力が明確（純粋関数に近い）**
   - 「入力データ → 変換 → 出力データ」の構造
   - ファイルI/Oが抽象化されている
   - サイドエフェクトが最小限

3. **不変条件（invariant）が定義できる**
   - 往復テスト（encode → decode == 元データ）
   - 冪等性（同じ入力で同じ出力）
   - 境界値が明確（空入力、最大値、特殊文字）

### ❌ テストが辛いプロジェクトの特徴

1. **テストがない or 脆弱**
   - 手動テスト頼み
   - 「動いてるように見える」が基準

2. **環境依存が強い**
   - タイミングに依存（race condition）
   - OS固有の機能（ioctl, mmap, inotify）
   - ネットワーク状態に依存

3. **出力が非決定的**
   - 時刻、乱数、PID が出力に混ざる
   - 並列実行で順序が変わる

## 現在避けるべき機能領域（moonbitlang/x 0.4.40 時点）

| 機能 | 状況 | 代替手段 |
|---|---|---|
| **stderr 出力** | `@sys` に API なし | `println` でフォールバック（TODO） |
| **is_symlink** | `@fs` に API なし | C FFI が必要 |
| **プロセス起動** | `std::process::Command` 相当なし | C FFI が必要 |
| **ソケット通信** | ネットワーク API なし | 不可 |
| **並列処理** | スレッドAPIが未成熟 | 同期・直列のみ |
| **メモリマップ** | mmap 相当なし | 不可 |
| **ターミナル制御** | termios, crossterm 相当なし | 自前ANSIのみ |

### 警告: API の破壊的変更が頻繁

fd_mbt で踏んだ変更例:

| 古い書き方 | 新しい書き方 |
|---|---|
| `starts_with("./")` | `has_prefix("./")` |
| `substring(2, len)` | `[2:]` |
| `s.to_bytes()` | `@encoding/utf8.encode(s)` |
| `"\x00"` | `"\u{0}"` |
| `match (try? expr)` | `try/catch/noraise` |

**対策**: `moon build` の警告を放置しない。deprecation 警告が出たら即対応。

## API 発見性の問題

`@sys` や `@fs` に何があるか知る方法が限られている:

```bash
# 現状の唯一の方法: .core バイナリを strings で漁る
strings _build/.../sys/sys.core | grep -i 'fn\|is_\|write'
```

**まともな API リファレンスがない**のが最大の DX 課題。

## 移植プロジェクト選定のチェックリスト

```
□ 1Hop でテストの充実が確認できるか？
   ├─ Codecov/Coveralls バッジがある
   ├─ GitHub Actions でテストが緑
   └─ tests/ ディレクトリ or *_test.* ファイルがある

□ 2. 入出力が明確か？
   ├─ 「入力X → 出力Y」の構造が明確
   ├─ 環境依存の出力が少ない
   └─ サイドエフェクトが最小限

□ 3. 必要な API が MoonBit にあるか？
   ├─ ファイルI/O: @fs で足りるか
   ├─ パス操作: @path で足りるか
   ├─ 正規表現: moonbitlang/regexp で足りるか
   └─ ネットワーク/プロセス: 不要か

□ 4. スコープが適切か？
   ├─ コア機能に絞れるか
   ├─ オプション機能は後回しにできるか
   └─ 1-2週間でMVPが出せるか
```

**4つ全て ✓ なら移植候補として適切。**

## fd_mbt で得た教訓

### やって良かったこと
- テストを最初に書いた（20件、全通過）
- スナップショットテスト + QuickCheck の併用
- `strip_cwd_prefix`, `null_separator` などの実用的な修正

### 反省点
- `exec` (`-x/-X`) をスタブのまま放置
- `filter` (size/time) をスタブのまま放置
- stderr 出力を `@sys` API がない時点で諦めた（TODO コメントのみ）
- `is_symlink` 検出を諦めた

### 次に活かすこと
- **MVP の線引きを明確に**: 「どこまでが必須機能か」を最初に決める
- **API 調査を最初にやる**: `strings .core | grep` で使える API をリストアップ
- **テストファースト**: 移植前にテストの骨格を作る
